   ```powershell

   helm repo add vm https://victoriametrics.github.io/helm-charts/
   ```

## 2. Подключение источника данных VictoriaMetrics (Data Source)

### 2.1. Конфигурация Data Source в Grafana
VictoriaMetrics полностью поддерживает протокол Prometheus HTTP API (`/api/v1/query`, `/api/v1/query_range`, `/api/v1/labels`). В связи с этим источник подключен с типом `prometheus` через встроенный механизм provisioning:

```yaml
apiVersion: 1
datasources:
  - name: VictoriaMetrics
    type: prometheus
    uid: VictoriaMetrics
    access: proxy
    url: http://vm-single-victoria-metrics-single-server.monitoring.svc.cluster.local:8428
    isDefault: true
    jsonData:
      httpMethod: POST
      timeInterval: 5s
```

### 2.2. Обоснование параметров подключения
* **`access: proxy`** — все запросы из браузера отправляются к Grafana Backend, который проксирует их во внутреннюю сеть Kubernetes кластера (`monitoring.svc.cluster.local`). Это обеспечивает безопасность (TSDB не торчит наружу) и исключает проблемы с CORS.
* **`isDefault: true`** — VictoriaMetrics назначена источником по умолчанию для всех панелей и шаблонизированных переменных.
* **`httpMethod: POST`** — запросы PromQL передаются в теле POST-запроса, что исключает ограничения веб-серверов по максимальной длине URL-строки при сложных агрегациях.
* **Проверка доступности (Health Check):**
  При обращении к `/api/datasources/1/health` Grafana возвращает:
  `{"status":"OK","message":"Successfully queried the Prometheus API."}`.

## 3. Дашборд приложения: методологии RED, USE и Golden Signals (6 баллов)

Дашборд **"Park PSU - Обзор приложения (RED & USE) и SLA Пробера"** объединяет высокоуровневый обзор жизнедеятельности сервиса для технического руководства и глубокую детализацию рантайма для разработчиков и инженеров эксплуатации.

```
┌───────────────────────────────────────────────────────────────────────────────────────────────────┐
│ Секция 1: Ключевые показатели сервиса (Golden Signals & SLA Пробера)                              │
│ [ SLA Пробера: 98.4% ]   [ RPS: 2.45 req/s ]   [ Ошибки: 0.12% ]   [ Средняя задержка: 14.2 ms ]  │
├───────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Секция 2: Методология RED (Rate, Errors, Duration)                                                │
│ 1. RPS по эндпоинтам и методам     2. Распределение кодов 2xx/4xx/5xx   3. Перцентили p50/p95/p99 │
├───────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Секция 3: Методология USE: Рантайм JVM (Память и Сборщик мусора)                                  │
│ 4. Память Heap: Used/Committed/Max 5. Память Non-Heap / Metaspace       6. Паузы GC Duration/Rate │
├───────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Секция 4: Методология USE: Потоки, CPU и Пул подключений БД HikariCP                              │
│ 7. Потоки JVM (Live/Daemon/Peak)   8. Утилизация CPU (Process vs Host)  9. Пул HikariCP (Act/Idle)│
│                                                                        10. Очередь и задержка пула│
└───────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 3.1. Секция 1: Ключевые показатели сервиса (Golden Signals)
Секция размещена в самом верху дашборда и отображает мгновенное здоровье системы в виде крупных числовых карточек (Stat) и кругового индикатора (Gauge):

1. **SLA Синтетического Пробера (Gauge):** отображает кумулятивный процент успешности зондирования сервиса за 30-минутное окно. *(Подробно описан в Разделе 4)*.
2. **Суммарный RPS сервиса (Requests Rate):**
   * *Метрика:* `sum(rate(http_server_requests_seconds_count[1m])) or vector(0)`
   * *Назначение:* отражает интенсивность трафика (Traffic Golden Signal).
3. **Доля ошибок API (HTTP Error Rate %):**
   * *Метрика:* `((sum(rate(http_server_requests_seconds_count{status=~"4..|5.."}[1m])) or vector(0)) / (sum(rate(http_server_requests_seconds_count[1m])) or vector(1))) * 100`
   * *Пороги:* Зелёный (< 1%), Жёлтый (1–5%), Красный (> 5%).
4. **Средняя задержка отклика (Average Latency):**
   * *Метрика:* `(sum(rate(http_server_requests_seconds_sum[1m])) / sum(rate(http_server_requests_seconds_count[1m]))) * 1000` (мс).
5. **Перцентиль хвостовой задержки P99 (Latency P99):**
   * *Метрика:* `(histogram_quantile(0.99, sum(rate(http_server_requests_seconds_bucket[1m])) by (le)) * 1000) or (sum(rate(http_server_requests_seconds_max[1m])) * 1000)`
   * *Назначение:* показывает время отклика для 1% наименее удачливых пользователей (хвостовая задержка).
6. **Доступные реплики бэкенда:** `count(up{app="backend"} == 1)`.
7. **Текущий статус синтетического зонда:** мгновенное состояние `HEALTHY` (200 OK) / `OFFLINE`.

---

### 3.2. Секция 2: Методология RED (Rate, Errors, Duration)
Методология RED (Tom Wilkie) ориентирована на микросервисную архитектуру и пользовательский опыт:

1. **Rate (Частота запросов по эндпоинтам):**
   * *Запрос:* `sum by (uri, method) (rate(http_server_requests_seconds_count[1m]))`
   * *Обоснование:* визуализация распределения потока вызовов между REST-эндпоинтами (`/api/parkingList`, `/api/login`, `/actuator/health`). Позволяет выявлять неожиданные всплески к отдельным контроллерам.
2. **Errors (Распределение HTTP-кодов 2xx, 4xx, 5xx):**
   * *Запросы:*
     * 2xx: `sum(rate(http_server_requests_seconds_count{status=~"2.."}[1m]))` (зелёный)
     * 4xx: `sum(rate(http_server_requests_seconds_count{status=~"4.."}[1m]))` (жёлтый)
     * 5xx: `sum(rate(http_server_requests_seconds_count{status=~"5.."}[1m]))` (красный)
   * *Обоснование:* график с накоплением (stacked) наглядно разделяет штатную нагрузку, клиентские ошибки аутентификации/валидации (401/403/404) и критические серверные сбои (500/503).
3. **Duration (Перцентили времени отклика p50, p95, p99):**
   * *Запросы:* расчет перцентилей по гистограмме Micrometer (`histogram_quantile(0.50|0.95|0.99, ...)`).
   * *Обоснование:* медиана (p50) демонстрирует типичное время отклика большинства пользователей, p95 отслеживает деградацию под нагрузкой, а p99 позволяет выявлять пиковые блокировки и GC-паузы.

---

### 3.3. Секция 3: Методология USE: Рантайм JVM (Память и Garbage Collection)
Методология USE (Brendan Gregg — Utilization, Saturation, Errors) применена для анализа здоровья виртуальной машины Java:

1. **Память JVM Heap (Used vs Committed vs Max):**
   * *Запросы:*
     * `sum(jvm_memory_used_bytes{area="heap"})` — занятая объектами память.
     * `sum(jvm_memory_committed_bytes{area="heap"})` — память, фактически выделенная ОС процессу JVM.
     * `sum(jvm_memory_max_bytes{area="heap"} > 0)` — предельный лимит кучи (`-Xmx`).
   * *Обоснование:* классический пилообразный график сборки мусора. Позволяет оперативно диагностировать утечки памяти (Memory Leaks), когда после циклов GC уровень Used Heap монотонно возрастает.
2. **Память JVM Non-Heap / Metaspace:**
   * *Запросы:* `sum(jvm_memory_used_bytes{area="nonheap", id="Metaspace"})` и кэш скомпилированного кода `CodeCache`.
   * *Обоснование:* мониторинг расхода памяти под метаданные загруженных классов и JIT-компиляцию.
3. **Паузы сборщика мусора GC (Duration & Rate):**
   * *Запросы:*
     * Время остановок: `sum(rate(jvm_gc_pause_seconds_sum[1m])) * 1000` (мс/с).
     * Частота пауз: `sum(rate(jvm_gc_pause_seconds_count[1m]))` (ops/s).
   * *Обоснование:* выявление пауз Stop-The-World (STW). Рост длительности пауз напрямую приводит к деградации перцентилей задержки приложения (p99 Latency).

---

### 3.4. Секция 4: Методология USE: Потоки, CPU и Пул подключений БД HikariCP
1. **Потоки JVM (Utilization & Saturation):**
   * *Запросы:* `jvm_threads_live_threads`, `jvm_threads_daemon_threads`, `jvm_threads_peak_threads`.
   * *Обоснование:* контроль пула потоков веб-сервера Tomcat/Jetty. Рост числа активных потоков свидетельствует о блокировках на внешних ресурсах (БД, сетевые вызовы).
2. **Утилизация CPU (Utilization):**
   * *Запросы:* `process_cpu_usage * 100` (процесс приложения) и `system_cpu_usage * 100` (хост-система).
   * *Обоснование:* контроль расхода процессорного времени и выявление троттлинга контейнера (CPU Throttling).
3. **Пул соединений HikariCP (Utilization):**
   * *Запросы:*
     * Занятые соединения: `hikaricp_connections_active`
     * Свободные соединения: `hikaricp_connections_idle`
     * Максимальный размер пула: `hikaricp_connections_max`
   * *Обоснование:* утилизация пула базы данных. Если active приближается к max, пул близок к исчерпанию.
4. **Насыщение HikariCP (Saturation & Latency):**
   * *Запросы:*
     * Запросы в очереди ожидания: `hikaricp_connections_pending` (потоки, ждущие соединение).
     * Максимальное время получения соединения: `hikaricp_connections_acquire_seconds_max * 1000` (мс).
   * *Обоснование:* главный симптом деградации взаимодействия с PostgreSQL — когда приложению не хватает коннектов, запросы встают в очередь `pending`, вызывая лавинообразный рост времени ответа REST API.

## 4. Выделенная панель подсчёта SLA пробера (3 балла)

В соответствии с требованиями задания подсчёт SLA синтетического зонда вынесен в **отдельную выделенную панель** на дашборде приложения:

### 4.1. Параметры панели
* **Название панели:** `SLA Синтетического Пробера (Healthcheck SLA %)`
* **Тип визуализации:** `Gauge` (круговой индикатор с динамической шкалой и процентным значением).
* **Источник данных:** `VictoriaMetrics`.

### 4.2. Формула расчёта (PromQL)
$$\text{Prober SLA} = \operatorname{clamp}\left(\operatorname{avg}\left(\operatorname{avg\_over\_time}(\texttt{app\_prober\_probe\_success}\{\texttt{target}="health"\}[30m])\right) \times 100, 0, 100\right)$$

```promql
clamp_max(clamp_min(avg(avg_over_time(app_prober_probe_success{target="health"}[30m])) * 100, 0), 100)
```

### 4.3. Обоснование выбора метрики и порогов
1. **Почему именно внешний синтетический пробер:**
   В отличие от внутренних метрик самого Spring Boot, внешний автономный микросервис (`prober-deployment`, Node.js 20) выступает независимым наблюдателем (Blackbox Probe). Он каждые 2 секунды выполняет полноценный сквозной HTTP-запрос через сеть Kubernetes кластера к `/actuator/health`. Если у пода бэкенда завис стек, упала сеть или исчерпаны потоки Tomcat, пробер зафиксирует сбой (`probe_success = 0`), точно отражая фактический опыт реальных пользователей.
2. **Скользящее окно 30 минут (`[30m]`):**
   Расчет SLA по скользящему окну сглаживает кратковременные секундные флуктуации сети и дает устойчивую кумулятивную оценку соблюдения контрактных обязательств.
3. **Цветовая дифференциация порогов (Thresholds):**
   * **Красный (0% – 94.99%):** `SLA Violated` — критическое нарушение гарантий надежности (сервис был недоступен более 1.5 минут за окно);
   * **Жёлтый/Оранжевый (95.0% – 97.99%):** `SLA At Risk` — фиксация инцидента, близкого к исчерпанию буфера безопасности;
   * **Тёмно-зелёный (98.0% – 99.49%):** `SLA Met` — соблюдение целевого контрактного уровня обслуживания (98.0%);
   * **Светло-зелёный (99.5% – 100%):** `Optimal` — идеальное состояние сервиса, соответствующее высшему уровню SLO.

## 5. Импорт и демонстрация дашборда PostgreSQL Exporter (1 балл)

### 5.1. Импортированный дашборд
В Grafana успешно импортирован официальный комьюнити-дашборд мониторинга PostgreSQL:
* **Название:** `PostgreSQL Database (Exporter 9628)`
* **Оригинал:** Grafana Community Dashboard ID **9628** (автор Lucas Estienne / Prometheus Community).
* **Источник данных:** `VictoriaMetrics` (метрики экспортируются сайдкар-контейнером `prometheuscommunity/postgres-exporter:v0.16.0` на порту 9187).

### 5.2. Адаптация и провижининг
1. Дашборд очищен от шаблонизированной переменной `DS_PROMETHEUS` и привязан к нашему источнику `VictoriaMetrics`.
2. Устранены жесткие фильтры `release="$release"`, которые требовали специфических Helm-меток Prometheus Operator. Переменные экземпляра (`instance`) и базы данных (`datname`) переведены на автоматический выбор из лейблов метрик: `label_values(pg_stat_database_xact_commit, datname)`.
3. Все PromQL-селекторы переведены на регулярные выражения `instance=~"$instance"`, что гарантирует корректное отображение данных при выборе значения `Instance: All` (`.*`) и предотвращает появление значений `N/A` на панелях настроек (`Settings`) и транзакций.
4. Для панели `Start Time` добавлена поддержка метрики `process_start_time_seconds`, экспортируемой текущей версией `postgres-exporter`.
5. Для графиков `Average Memory Usage` и `Average CPU Usage` исправлены запросы (убран ошибочный вызов `rate()` на gauge-метрику resident memory, добавлен фильтр `app="postgres"`).
6. Дашборд сохранён в файл `postgres_dashboard.json` и автоматически монтируется в Grafana через ConfigMap `grafana-dashboard-postgres`.

### 5.3. Отображаемые ключевые метрики СУБД
Дашборд включает 35 детальных панелей:
1. **PostgreSQL Service Uptime & Status:** статус доступности СУБД (`pg_up == 1`), время аптайма сервера.
2. **Transactions Throughput (TPS):** скорость фиксации транзакций (`pg_stat_database_xact_commit`) и откатов (`pg_stat_database_xact_rollback`).
3. **Cache Hit Ratio (%):**
   $$\text{Cache Hit Ratio} = \frac{\texttt{pg\_stat\_database\_blks\_hit}}{\texttt{pg\_stat\_database\_blks\_read} + \texttt{pg\_stat\_database\_blks\_hit}} \times 100\%$$
   Показывает процент чтения блоков из оперативной памяти (Shared Buffers) без обращения к диску (на нашей тестовой базе составляет `> 99%`).
4. **Database Size:** динамика физического размера БД `park_psu` в байтах (`pg_database_size_bytes`).
5. **Active vs Idle Sessions:** количество активных и простаивающих клиентских сессий бэкенда (`pg_stat_activity_count`).
6. **Locks & Conflicts:** количество блокировок таблиц (`pg_locks_count`), взаимоблокировок (`deadlocks`) и конфликтов.
7. **Tuple Activity:** активность чтения и модификации кортежей: `tup_fetched`, `tup_inserted`, `tup_updated`, `tup_deleted`.

## 6. Скриншоты дашбордов и панелей

### 6.1. Дашборд приложения: Golden Signals и SLA Пробера
