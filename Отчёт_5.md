## 3. Формулировки SLI, SLO и SLA и математические формулы

### 3.1. SLI 1: Доступность API (API Availability — RBSLO)

#### Формулировка SLI
Доля успешных HTTP-запросов к REST API бэкенда (HTTP-статусы `2xx`) к общему объёму всех поступивших валидных запросов за скользящее окно мониторинга в 20 секунд.

#### Математическая формула мгновенного SLI
$$\text{SLI}_{\text{avail}} = \frac{\sum \text{Requests with status } 2xx}{\sum \text{Total Valid Requests}} \times 100\%$$

#### PromQL / MetricsQL запрос в VictoriaMetrics / Grafana:
```promql
clamp_max(clamp_min((sum(rate(http_server_requests_seconds_count{status=~"2.."}[20s])) or vector(1)) / (sum(rate(http_server_requests_seconds_count[20s])) or vector(1)) * 100, 0), 100)
```

#### Внутренний инженерный SLO
* **Целевой показатель:** **99.0%** успешных ответов.
* **Окно соответствия (Evaluation Window):** Скользящие 30 календарных дней.
* **Допустимый лимит деградации:** Бюджет ошибок составляет $100\% - 99.0\% = 1.0\%$ от общего числа запросов.

#### Соглашение SLA приложения
* **Формулировка SLA:** Доля успешных валидных HTTP-запросов к REST API (статусы `2xx`) за отчётный календарный месяц должна составлять не менее **95.0%** от общего числа валидных запросов.
* **Расчетный период:** **1 календарный месяц** (с 00:00:00 1-го числа по 23:59:59 последнего дня месяца).
* **Как считается SLA за период:**
  $$\text{SLA}_{\text{avail\_month}} = \frac{\sum_{i=1}^{N_{\text{month}}} R_{2xx, i}}{\sum_{i=1}^{N_{\text{month}}} R_{\text{valid}, i}} \times 100\%$$
  где $R_{2xx, i}$ — число успешных ответов за месяц, $R_{\text{valid}, i}$ — общее число валидных запросов за месяц.
* **Исключения:**
  Из подсчета валидных запросов исключаются ошибки $4xx$, вызванные некорректным поведением клиентов (неверные учетные данные, запросы к несуществующим адресам), а также время согласованных плановых работ.

---

### 3.2. SLI 2: Задержка обработки запросов (API Latency — RBSLO)

#### Формулировка SLI
Доля времени работы сервиса, при которой среднее время обработки запросов не превышает допустимый критерий в 200 миллисекунд ($0.2$ с).

#### Математическая формула
Средняя задержка обработки запросов за окно в 20 секунд (сквозная задержка пробера, либо бэкенда):
$$\text{Latency}_{\text{avg}} = \text{avg\_over\_time}(\text{app\_prober\_probe\_duration\_seconds}[20s])$$

$$\text{SLI}_{\text{latency}} = \max\left(0, \min\left(100, \left(1 - \frac{\text{Latency}_{\text{avg}}}{0.200}\right) \times 100\right)\right)$$

#### PromQL / MetricsQL запрос в VictoriaMetrics / Grafana:
```promql
clamp_max(clamp_min((1 - ((avg(avg_over_time(app_prober_probe_duration_seconds{target="health"}[20s])) or ((sum(rate(http_server_requests_seconds_sum[20s])) or vector(0.01)) / (sum(rate(http_server_requests_seconds_count[20s])) or vector(1)))) / 0.200)) * 100, 0), 100)
```

#### Внутренний инженерный SLO
* **Целевой показатель:** **95.0%** времени работы сервиса время отклика не должно превышать 200 мс.
* **Окно соответствия:** Скользящие 30 дней.

#### Соглашение SLA приложения
* **Формулировка SLA:** Доля времени работы сервиса в течение отчётного календарного месяца, при которой средняя задержка отклика не превышает 200 мс ($0.200$ с), должна составлять не менее **90.0%**.
* **Расчетный период:** **1 календарный месяц** (с 00:00:00 1-го числа по 23:59:59 последнего дня месяца, 43 200 минут при 30-дневном месяце).
* **Как считается SLA за период (TBSLO):**
  $$\text{SLA}_{\text{latency\_month}} = \frac{T_{\text{month}} - T_{\text{latency\_degraded}}}{T_{\text{month}} - T_{\text{scheduled\_maintenance}}} \times 100\%$$
  где $T_{\text{month}}$ — общее количество минут в месяце, $T_{\text{latency\_degraded}}$ — суммарное число минут в месяце, когда средняя задержка превышала $0.200$ с (допускается не более 10%, то есть $\le 4\,320$ минут за месяц), $T_{\text{scheduled\_maintenance}}$ — время плановых регламентных работ.

---

### 3.3. SLI 3: Доступность по внешнему синтетическому проберу (Prober Success Rate — TBSLO / RBSLO)

#### Формулировка SLI
Отношение успешных сквозных проверок ключевого эндпоинта (`/actuator/health`), непрерывно выполняемых внешним независимым подом `prober` каждые 2 секунды, к общему числу выполненных проверок.

#### Математическая формула
$$\text{SLI}_{\text{prober}} = \frac{\text{Successful Probes}}{\text{Total Probes}} \times 100\% = \text{avg\_over\_time}(\text{app\_prober\_probe\_success}[20s]) \times 100\%$$

#### PromQL / MetricsQL запрос в VictoriaMetrics / Grafana:
```promql
clamp_max(clamp_min(avg(avg_over_time(app_prober_probe_success{target="health"}[20s])) * 100, 0), 100)
```

#### Внутренний инженерный SLO
* **Целевой показатель:** **99.5%** успешных зондирований.
* **Окно соответствия:** Скользящие 30 дней.

#### Соглашение SLA приложения
* **Формулировка SLA:** Доля успешных синтетических проверок доступности эндпоинта `/actuator/health` внешним пробером за отчётный календарный месяц должна составлять не менее **98.0%** от общего числа проб.
* **Расчетный период:** **1 календарный месяц** (порядка $1\,296\,000$ тестовых проб при интервале 2 секунды).
* **Как считается SLA за период:**
  $$\text{SLA}_{\text{prober\_month}} = \frac{\sum_{k=1}^{M_{\text{month}}} P_{\text{success}, k}}{M_{\text{month}}} \times 100\%$$
  где $P_{\text{success}, k} \in \{0, 1\}$ — результат $k$-й пробы, $M_{\text{month}}$ — общее количество проб за календарный месяц (за вычетом времени планового обслуживания).

---

### 3.4. Общий составной (Composite) SLA для сервиса Park PSU

#### Формулировка composite SLA
Общий SLA для программно-аппаратного комплекса Park PSU формулируется как одновременное выполнение всех трёх соглашений об уровне обслуживания за отчётный календарный месяц:

$$\text{SLA}_{\text{composite}} = (\text{SLA}_{\text{avail\_month}} \ge 95.0\%) \land (\text{SLA}_{\text{latency\_month}} \ge 90.0\%) \land (\text{SLA}_{\text{prober\_month}} \ge 98.0\%)$$

* **Расчетный период:** **1 календарный месяц** (с 00:00:00 1-го числа по 23:59:59 последнего дня месяца).
* **Как считается:** По окончании отчётного месяца для каждого из трёх индикаторов вычисляется итоговый показатель за весь период (накопительным итогом, без учёта согласованного планового обслуживания и клиентских ошибок 4xx). Если хотя бы по одному из трёх критериев значение ниже установленного порога, SLA за месяц считается невыполненным.

---

### 3.5. Концепция и формула бюджета ошибок (Error Budget)

#### Связь бюджета ошибок с SLO:
В методологии Google SRE бюджет ошибок рассчитывается строго относительно внутреннего **SLO** ($99.0\%$):
$$\text{Error Limit} = 100\% - \text{SLO} = 100\% - 99.0\% = 1.0\%$$

Разница между внутренним SLO ($99.0\%$) и внешним SLA ($95.0\%$) формирует **защитный буфер безопасности (Safety Buffer)**:
$$\text{Safety Buffer} = \text{SLO} - \text{SLA} = 99.0\% - 95.0\% = 4.0\%$$

**Смысл существования буфера:** Инженерная команда расходует бюджет ошибок. Когда бюджет сгорает до $0\%$, объявляется мораторий на деплой непроверенных изменений (Feature Freeze). В этот момент сервис работает с надежностью около $99.0\%$, что значительно выше порога SLA ($95.0\%$). Таким образом, команда останавливает деградацию **до того**, как будет нарушено соглашение SLA перед пользователями!

#### Математическая формула остатка бюджета ошибок:
$$\text{Error Rate} = \frac{\sum \text{rate}(http\_server\_requests\_seconds\_count\{status!\sim "2.." \}[20s])}{\sum \text{rate}(http\_server\_requests\_seconds\_count[20s])}$$

$$\text{Error Budget Remaining} = \max\left(0, \min\left(100, 100\% - \frac{\text{Error Rate}}{\text{Error Limit}} \times 100\%\right)\right)$$

#### PromQL запрос в Grafana:
```promql
clamp_max(clamp_min(100 - (((sum(rate(http_server_requests_seconds_count{status!~"2.."}[20s])) or vector(0)) / (sum(rate(http_server_requests_seconds_count[20s])) or vector(1))) / 0.01 * 100), 0), 100)
```

## 4. Архитектура и реализация автономного пробера

В соответствии с принципами 12-Factor App (Факторы VI Processes и VII Port Binding) пробер спроектирован как изолированный сервис `prober-deployment` в Kubernetes:

```
+----------------------------------------------------------------------------------------------------+
| Pod: prober-deployment (Node.js 20 Alpine)                                                         |
|                                                                                                    |
|  [Синтетический зонд (каждые 2 сек)] ---- GET /actuator/health ----> Pod: backend-deployment       |
|    * Замер кода статуса (200 OK / 503 Service Unavailable)                                         |
|    * Высокоточный замер длительности отклика (process.hrtime)                                      |
|                                                                                                    |
|  [Интерфейс управления авариями и задержкой]:                                                      |
|    * POST /fail    -> имитация отказа сервиса (probe_success = 0, status = 503)                     |
|    * POST /recover -> снятие аварии (probe_success = 1, status = 200)                              |
|    * POST /delay   -> имитация высокой сетевой задержки (artificial delay 350 мс > SLO 200 мс)     |
|    * POST /nodelay -> возврат к нормальной задержке (< 5 мс)                                       |
|                                                                                                    |
|  [OpenMetrics HTTP Server :9090/metrics]:                                                          |
|    * app_prober_probe_success (Gauge: 1 или 0)                                                     |
|    * app_prober_probe_duration_seconds (Gauge: задержка отклика)                                   |
|    * app_prober_probes_total (Counter: счетчик успешных и сбойных проб)                            |
+----------------------------------------------------------------------------------------------------+
                                      |
                         Scrape каждые 10 секунд (Service Discovery)
                                      v
                      TSDB VictoriaMetrics (хранение временных рядов)
```

## 5. Описание сценария изменения поведения приложения для скринкаста

Для наглядного подтверждения динамики графиков SLI, SLO и SLA подготовлен сценарий автоматизированной нагрузки `simulate_slo_traffic.js`. Сценарий включает 5 последовательных фаз, каждая из которых демонстрирует отклик соответствующего индикатора:

1. **Фаза 1: Штатный режим работы (20 секунд):**
   * Сервис функционирует в нормальном режиме (штатные 200 OK запросы к `/actuator/health`, отсутствие искусственных задержек).
   * Все индикаторы SLI находятся в зелёной зоне выше целевых порогов SLO, бюджет ошибок полон, показатель SLA фиксирует полное соблюдение соглашения.
2. **Фаза 2: Деградация времени отклика (API Latency) (20 секунд):**
   * Вызов эндпоинта `/delay` на внешнем пробере моделирует сетевую задержку (350 мс при нормативе 200 мс).
   * **Результат на графике SLI 2:** временной ряд задержки опускается ниже линии порога SLO (95.0%), в то время как доступность (SLI 1) остаётся на высоком уровне (ошибок нет, сервис работает медленно). По завершении фазы вызывается `/nodelay`.
3. **Фаза 3: Контролируемый расход бюджета ошибок (25 секунд):**
   * Генерация потока сбойных запросов с кодом `403 Forbidden` (`/api/parkingList`).
   * **Результат:** внутренний инженерный порог SLO по доступности нарушается, на панели `Остаток бюджета ошибок` наблюдается расходование Error Budget, в то время как интегральный SLA остаётся в безопасной зоне.
4. **Фаза 4: Критический сбой и авария (25 секунд):**
   * Увеличение доли ошибочных запросов к API и перевод пробера в аварийный режим (`/fail`, код 503).
   * **Результат:**
     * График доступности API (`SLI 1`) и успешность пробера (`SLI 3`) уходят в аварийную зону;
     * Бюджет ошибок (`Error Budget Remaining`) полностью исчерпывается до 0%;
     * Накопительный показатель на панели `Мониторинг соблюдения SLA сервиса` опускается ниже пороговой границы 95.0%.
5. **Фаза 5: Полное восстановление работоспособности (20 секунд):**
   * Возврат пробера в рабочий режим (`/recover`) и прекращение генерации ошибок.
   * Все индикаторы SLI и остаток бюджета ошибок синхронно возвращаются в штатную зелёную зону.

## 6. Результаты проверки и отображение в Grafana и vmui

### 6.1. Архитектура компактного дашборда Grafana (One-Screen Layout)
В Grafana развернут и автоматически провижинится компактный дашборд **«Park PSU - SRE Мониторинг SLI / SLO / SLA»**, состоящий из 5 панелей в два ряда. Дашборд полностью помещается на стандартном экране 1920×1080 без вертикального скролла:

```
+-------------------------------------------------------------------------------------------------------+
| РЯД 1: Динамика индикаторов во времени vs Инженерные пороги SLO (Timeseries)                          |
|  [SLI 1: API Availability %]       |  [SLI 2: API Latency Score %]      |  [SLI 3: Prober Success %]  |
|  (SLI во времени vs SLO 99.0%)     |  (SLI во времени vs SLO 95.0%)     |  (SLI во времени vs 99.5%)  |
+-------------------------------------------------------------------------------------------------------+
| РЯД 2: Бюджет ошибок (Error Budget) и мониторинг выполнения контракта SLA                             |
|  [Остаток Error Budget Remaining %] (с линией отсечки 0%) | [Мониторинг соблюдения SLA (порог 95%)]   |
+-------------------------------------------------------------------------------------------------------+
```

* **Панель 1 (Timeseries SLI 1):** Временной ряд доступности API бэкенда с горизонтальной линией целевого инженерного SLO (99.0%) и табличной легендой с текущим значением (`Last`).
* **Панель 2 (Timeseries SLI 2 — API Latency):** График соблюдения норматива по задержке отклика (< 200 мс) и линия инженерного порога SLO (95.0%).
* **Панель 3 (Timeseries SLI 3):** Временной ряд сквозных проверок внешнего синтетического пробера и линия порога SLO (99.5%).
* **Панель 4 (Timeseries Error Budget Remaining %):** График расхода допустимого бюджета ошибок с линией 0% (сигнал к Feature Freeze).
* **Панель 5 (Gauge SLA Compliance):** Интегральная накопительная панель, отражающая кумулятивную доступность API (`SLI 1`) за скользящее расчетное окно с пороговой границей контрактного обязательства SLA 95.0%.
* (В регламенте сервиса SLA рассчитывается кумулятивно за календарный месяц. В рамках данного стенда для наглядной демонстрации на скринкасте настроено модельное пятиминутное окно, чтобы наглядно посмотреть, как сбой влияет на показатель SLA, пробив контрактный порог 95%)
