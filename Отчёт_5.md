## 2. Описание выбранных метрик для расчета доступности

Для комплексной оценки качества работы сервиса Park PSU выбраны 4 метрики, покрывающие как модель **RBSLO (Request Based SLO)**, так и **TBSLO (Time Based SLO)**:

| № | Имя метрики в TSDB | Источник | Тип метрики | Описание |
|---|--------------------|----------|-------------|----------|
| **1** | `http_server_requests_seconds_count` | Spring Boot Actuator / Micrometer | Counter | Общее количество входящих HTTP-запросов к REST API бэкенда с разбивкой по HTTP-методам, эндпоинтам и статусам ответов (`status="200"`, `status="500"`, `status="403"`). |
| **2** | `http_server_requests_seconds_sum` | Spring Boot Actuator / Micrometer | Counter (Seconds) | Суммарное время обработки HTTP-запросов сервером. Позволяет рассчитывать среднюю задержку (Latency) как отношение `sum / count`. |
| **3** | `app_prober_probe_success` | Автономный Kubernetes-пробер (`k8s/10-prober.yaml`) | Gauge (0 или 1) | Бинарный индикатор успешности синтетического зондирования сервиса независимым клиентом (1 — запрос успешен, код < 400; 0 — сетевая ошибка, таймаут или 5xx). |
| **4** | `up{job="kubernetes-pods", app="backend"}` | VictoriaMetrics Agent (Service Discovery) | Gauge (0 или 1) | Индикатор доступности подов бэкенда при периодическом опросе со стороны сборщика метрик (TBSLO Uptime). |

## 3. Формулировки SLI, SLO и SLA и математические формулы

### 3.1. SLI 1: Доступность API (API Availability — RBSLO)
* **Формулировка SLI:** Доля успешных HTTP-запросов к бэкенду (HTTP-статусы `2xx`) к общему количеству поступивших запросов.
* **Математическая формула:**
  $$\text{SLI}_{\text{avail}} = \frac{\sum \text{Requests with status } 2xx}{\sum \text{Total Requests}} \times 100\%$$
* **PromQL / MetricsQL запрос в VictoriaMetrics / Grafana:**
  ```promql
  clamp_max(clamp_min((sum(rate(http_server_requests_seconds_count{status=~"2.."}[20s])) or vector(1)) / (sum(rate(http_server_requests_seconds_count[20s])) or vector(1)) * 100, 0), 100)
  ```
* **Целевой SLO:** **99.0%** успешных запросов за скользящее окно мониторинга.
* **SLA сервиса:** **95.0%**. При падении доступности ниже 95% за отчетный период предусматриваются компенсации заказчику/пользователям согласно регламенту.
* **Бюджет ошибок (Error Budget):**
  $$\text{Error Budget} = 100\% - 95.0\% = 5.0\% \text{ допустимых ошибок до нарушения SLA}$$

---

### 3.2. SLI 2: Задержка обработки запросов (API Latency — RBSLO)
* **Формулировка SLI:** Доля времени работы, при которой среднее время отклика бэкенда не превышает допустимый порог в 200 миллисекунд ($0.2$ с).
* **Математическая формула:**
  $$\text{Latency} = \frac{\sum \text{rate}(http\_server\_requests\_seconds\_sum)}{\sum \text{rate}(http\_server\_requests\_seconds\_count)}$$
  $$\text{SLI}_{\text{latency}} = \max\left(0, \min\left(100, \left(1 - \frac{\text{Latency}}{0.200}\right) \times 100\right)\right)$$
* **PromQL / MetricsQL запрос в VictoriaMetrics / Grafana:**
  ```promql
  clamp_max(clamp_min((1 - ((sum(rate(http_server_requests_seconds_sum[20s])) or vector(0.01)) / (sum(rate(http_server_requests_seconds_count[20s])) or vector(1)) / 0.200)) * 100, 0), 100)
  ```
* **Целевой SLO:** **95.0%** запросов должны обрабатываться быстрее 200 мс.
* **SLA сервиса:** **90.0%**.

---

### 3.3. SLI 3: Доступность по внешнему синтетическому проберу (Prober Success Rate — TBSLO / RBSLO)
* **Формулировка SLI:** Процент успешных синтетических проверок (зондирований ключевого эндпоинта `/actuator/health`), выполняемых внешним независимым подом `prober` каждые 2 секунды.
* **Математическая формула:**
  $$\text{SLI}_{\text{prober}} = \frac{\text{Successful Probes}}{\text{Total Probes}} \times 100\% = \text{avg\_over\_time}(\text{app\_prober\_probe\_success}[20s]) \times 100\%$$
* **PromQL / MetricsQL запрос в VictoriaMetrics / Grafana:**
  ```promql
  clamp_max(clamp_min(avg(avg_over_time(app_prober_probe_success{target="health"}[20s])) * 100, 0), 100)
  ```
* **Целевой SLO:** **99.5%** успешных зондирований.
* **SLA сервиса:** **98.0%**.

---

### 3.4. Общий composite SLA для сервиса Park PSU
Общий SLA для программного комплекса Park PSU формулируется как одновременное выполнение всех трех соглашений:
$$\text{SLA}_{\text{total}} = (\text{SLI}_{\text{avail}} \ge 95.0\%) \land (\text{SLI}_{\text{latency}} \ge 90.0\%) \land (\text{SLI}_{\text{prober}} \ge 98.0\%)$$
Если в течение расчетного месяца хотя бы один из показателей падает ниже установленного порога SLA, фиксируется нарушение соглашения об уровне обслуживания.

---

### 3.5. Формула и расчёт остатка бюджета ошибок (Error Budget Remaining)
Бюджет ошибок — это допустимый объем ненадёжности сервиса до момента наступления ответственности по SLA:
* **Допустимый лимит ошибок по SLA:**
  $$\text{Error Limit} = 100\% - \text{SLA} = 100\% - 95.0\% = 5.0\%$$
* **Текущая доля ошибок (Error Rate):**
  $$\text{Error Rate} = \frac{\sum \text{rate}(http\_server\_requests\_seconds\_count\{status!\sim "2.." \})}{\sum \text{rate}(http\_server\_requests\_seconds\_count)}$$
* **Остаток бюджета ошибок (Error Budget Remaining %):**
  $$\text{Error Budget Remaining} = \max\left(0, \min\left(100, 100\% - \frac{\text{Error Rate}}{\text{Error Limit}} \times 100\%\right)\right)$$
* **PromQL запрос в панели Grafana:**
  ```promql
  clamp_max(clamp_min(100 - (((sum(rate(http_server_requests_seconds_count{status!~"2.."}[20s])) or vector(0)) / (sum(rate(http_server_requests_seconds_count[20s])) or vector(1))) / 0.05 * 100), 0), 100)
  ```
* **Поведение формулы на этапах:**
  * $\text{Error Rate} = 0\% \implies \text{Remaining} = 100\%$ (зеленый сектор, штатный режим);
  * $\text{Error Rate} = 2.5\% \implies \text{Remaining} = 100\% - \frac{2.5\%}{5.0\%} \times 100\% = 50\%$ (желтый сектор, контролируемый расход бюджета);
  * $\text{Error Rate} \ge 5.0\% \implies \text{Remaining} = 0\%$ (красный сектор, полное исчерпание бюджета, фиксация на нуле без ухода в минус благодаря `clamp_min`).

## 4. Архитектура и реализация автономного пробера

В соответствии с принципами 12-Factor App (Факторы VI Processes и VII Port Binding) пробер реализован как отдельный независимый сервис `prober-deployment` в Kubernetes:
1. **Код пробера (`k8s/10-prober.yaml`):**
   * Легковесный сервис на Node.js 20 Alpine.
   * Выполняет непрерывные циклы зондирования HTTP эндпоинта приложения внутри кластера с интервалом 3 секунды.
   * Фиксирует статус, код ответа и точную длительность зондирования в наносекундах (`process.hrtime`).
2. **Экспорт метрик (OpenMetrics):**
   * Пробер открывает порт `9090` и отдает метрики в стандартном Prometheus-формате:
     * `app_prober_probe_success` (Gauge, 1 или 0);
     * `app_prober_probe_duration_seconds` (Gauge, задержка отклика);
     * `app_prober_probes_total` (Counter, счетчик успешных и сбойных проб).
3. **Автообнаружение:**
   * Под пробера снабжен аннотациями `prometheus.io/scrape: "true"` и `prometheus.io/port: "9090"`, благодаря чему агент `vmagent` автоматически обнаруживает его и непрерывно передает временные ряды в TSDB VictoriaMetrics.

## 5. Описание сценария изменения поведения приложения для скринкаста

Для демонстрации динамики изменения графиков SLI, SLO и расхода бюджета ошибок подготовлен сценарий `simulate_slo_traffic.js`. Сценарий включает 4 четко выраженные фазы:

```
[Фаза 1: Норма] ----> [Фаза 2: Нагрузка] ----> [Фаза 3: Критический сбой] ----> [Фаза 4: Восстановление]
  SLI = 100%            SLI ~ 97-98%             SLI падает до ~20%                SLI = 100%
  Budget = 100%         Budget ~ 50%             Budget = 0%                       Budget = 100%
  Prober = 100%         Prober = 100%            Prober = 0%                       Prober = 100%
```

1. **Фаза 1: Нормальная работа сервиса (20 секунд):**
   * Отправка штатных запросов к эндпоинтам бэкенда (`/actuator/health`).
   * **Результат:** `SLI Availability` держится на уровне **100%** (зеленый), превышая целевой порог SLO (99%). `Error Budget Remaining` равен **100%**. Внешний пробер фиксирует 100% успешность.
2. **Фаза 2: Умеренная нагрузка и контролируемый расход бюджета ошибок (25 секунд):**
   * Генерация потока запросов с долей ошибок ~2.5% (половина от допустимого лимита SLA 5.0%).
   * **Результат:** `SLI Availability` опускается до **~97.5%** (нарушен SLO 99%, но SLA 95% соблюден). На панели `Error Budget Remaining` отображается плавный контролируемый расход бюджета ошибок со 100% до **~50%** (желто-оранжевая зона). Это иллюстрирует главную идею SRE: команда видит деградацию бюджета до того, как нарушится SLA!
3. **Фаза 3: Критический сбой и авария (30 секунд):**
   * Резкое увеличение доли ошибок до 80% (`/api/parkingList` с кодом 403) и программный вызов эндпоинта аварии пробера (`/fail`).
   * **Результат:**
     * `SLI Availability` глубоко падает до **~20%** (красная зона, существенное нарушение SLA 95%);
     * `SLI 3 (Пробер)` падает до **0%**;
     * `Error Budget Remaining` сгорает до **0%** и фиксируется на нулевой линии (без ухода в отрицательные значения благодаря ограничению `clamp_min`).
4. **Фаза 4: Восстановление сервиса (25 секунд):**
   * Восстановление внешнего пробера (`/recover`) и прекращение отправки ошибок (100% успешных запросов).
   * **Результат:** Все шкалы и временные ряды SLI и бюджета ошибок синхронно возвращаются к **100%**.
